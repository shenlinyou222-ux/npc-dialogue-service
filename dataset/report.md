## 2. 四个问题的修复情况

### ① 训练/推理格式不一致 ⭐（最重要）

**根因（实测数据）**：用同一个解析器拆解旧数据的 user 段，发现

| 问题 | 旧数据实测 | v2 |
|---|---|---|
| `【场景：】` 与 `【任务：】` 挤在同一行 | **100.0%** | **0.0%** |
| 含 `【任务：XXX】` 这种推理时不存在的元数据 | 97.8% | **0.0%** |
| 结构化样本内部混入无说话人裸行 | 1253 条 | **0 条** |
| 推理主力形态 `【场景：】+对话历史` 的覆盖 | 4906 条但**场景行全被污染** | 643 条**结构正确** |
| 推理场景①`（动作）` 形态 | **0 条** | 215 条 |

旧数据即使把 `【任务：】` 删掉，其场景行仍与任务名同行、且任务名本身就是 Wiki 元数据，
**不可能**构成推理时那个独立的 `【场景：X】` 行 —— 这就是"格式完全不同"的结构性根因。

**v2 做法**：user 段只由 `【场景：<推断描述>】` + `说话人：台词` / `（动作）` 组成，
不再承载任何 Wiki 元数据；场景描述从 `region` + `section` + 上下文关键词推断；
并且**同时覆盖推理实测的 4 种输入形态**。

**覆盖率**（v2 实测）：

| variant | 形态 | 训练集占比 | 对应推理场景 |
|---|---|---|---|
| `scene_dialogue` | `【场景：X】` + 说话人历史 | 56.6% | 战斗前/战斗后/看雪/回忆/危险/告别 |
| `scene_action` | `【场景：X】` + `（动作）` | 10.3% | 看雪 |
| `bare_action` | `（动作）` | 15.8% | 打招呼 |
| `bare_line` | 一句话 | 17.2% | 被夸奖/抱怨累/感谢 |

### ② 样本严重冗余

以「三月七发言游程的连续片段」为最小单位，一个 mission 产出 2–5 条。
`每 mission 平均样本数 29.8 → 6.6`，而 `覆盖 mission 183 → 207`。
同时去掉了 33 条完全重复 + 7 条同 mission 内重复台词。

### ③ 输出过短

三项措施：
1. 连续多轮台词**合并**成一段 assistant（`--max-merge-lines 2`，由 `calibrate.py` 标定）；
2. 长游程**切块**，前一块进入上下文 → 形成"同场景不同切片"的续写样本（271 条）；
3. 单行游程只保留 `>=24` 字的长台词。

结果：assistant 均值 **13.9 → 28.9 token**（+108%），落在父代理给的 **20–30 token** 目标区间内。

**⚠ 需要父代理注意的一个权衡**：这里存在两个略有出入的目标 ——
父代理最初的任务书写的是「25–40 token」，后续补充消息写的是「20–30 token，对齐真实台词 27 字」。
本数据取 **28.9 token（46.1 字）**，落在两者的**交集**内（既是 20–30 的上沿，也是 25–40 的中段）。
如果父代理更希望**严格贴合真实台词长度（16.8 token / 27 字）**，可改用 `cap=1 + 少量长单行`，
但这会让多轮合并样本消失、削弱问题③的修复力度，建议先按当前版本训练再评估。

### ④ 无多样性

4 种输入形态 × 2/3/4 轮上下文窗口 × 3 种 channel（mission/sms/voice/choice）× region 分层配额。
长游程切片 + 角色语音层提供同场景的多种反应。

## 3. 格式一致性检查结果（训练格式 vs 推理格式）

检查脚本 `check_format.py` 以**真实推理 prompt 为基准** —— 逐字取自 `/home/user/vcf.py`
的 10 条场景矩阵（即父代理验证 LoRA 时实际发出去的输入），脚本会自动核对它们
是否仍与该文件逐字一致。然后把基准 prompt 与训练数据的 user 段各自解析成**结构签名**做比对。

```
[0] 基准 prompt 溯源
    ✓ 10 条基准 prompt 与 /home/user/vcf.py 逐字一致（推理真实输入）
    推理输入的形状分布: {'scene_dialogue': 5, 'scene_action': 1, 'bare_action': 1, 'bare_line': 3}

[2] 硬检查
    ✓ 元数据污染 = 0（无任何样本含【任务：】等 Wiki 元数据）
    ✓ 形状覆盖完整：推理用到的 4 种形状训练数据全部具备
    ✓ 结构化样本中「每轮都带说话人或（动作）」: 908/908 = 100.0%
    ✓ 玩家说话人名与推理一致（开拓者）: 出现 395 次
    ✓ 场景描述全部非空、非泛化、长度合理（<=30 字）
    ✓ 场景行与 Wiki 元数据同行（被污染）的样本: 0

[3] 与 10 条真实推理输入逐条对齐
    打招呼  bare_action     ✓      战斗前  scene_dialogue  ✓
    被夸奖  bare_line       ✓      战斗后  scene_dialogue  ✓
    抱怨累  bare_line       ✓      看雪    scene_action    ✓
    回忆    scene_dialogue  ✓      危险    scene_dialogue  ✓
    告别    scene_dialogue  ✓      感谢    bare_line       ✓

结论：✓ 通过 —— 训练 user 段与真实推理 prompt 结构一致
```

**结论**：训练 user 段与推理 prompt 在**结构上一致** —— 都是「场景 + 带说话人的对话历史」
或「场景 + 动作」，都不含 Wiki 元数据，且推理用到的 4 种形态全部有对应样本。

## 5. assistant 长度分布 vs 真实原句长度分布

参考数据：`E:\habitica-setup\job\gold-compare.json`（10 条真实三月七台词 + 基座/LoRA 输出）。

| 来源 | char 均值 | token 均值 | token p50 | token p90 |
|---|---|---|---|---|
| 真实原句 gold（n=10） | 27.0 | 16.8 | 18 | 34 |
| 旧 LoRA 推理输出（n=10） | 8.5 | 6.0 | 6 | 12 |
| 基座模型 推理输出（n=10） | 107.4 | 71.6 | 80 | 80 |
| **★ 新训练集 assistant（n=1357）** | **46.1** | **28.9** | **27** | **45** |
| 旧训练集 assistant（n=5092） | 21.9 | 13.9 | 12 | 25 |

**解读**：

- 旧训练集 assistant 均值 13.9 token，只有真实原句（16.8）的 **83%**，
  且 p50 仅 12 —— 训练信号本身就在教模型"简短地回答"，这直接解释了
  LoRA 推理输出只有 8.5 字（真实原句的 31%）。
- 新训练集 assistant 均值 28.9 token = 真实原句的 **1.72×**。**这是有意为之**：
  考虑到旧 LoRA 输出**严重压缩**（gold 16.8 → 输出 6.0 token，压缩到 36%），
  训练目标必须显著高于真实长度才能把推理输出"拉"回真实区间。
  预期效果：推理输出从 6.0 token 提升至 10–16 token，接近真实原句。
- 新数据的 p50=27 / p90=45，覆盖了 gold 的 p50=18 / p90=34 —— 分布区间是匹配的。

> **诚实说明**：以上"预期效果"是**推断**，尚未经训练验证（本任务只做数据、不训练）。
> 真实效果需跑完训练 + `vcf.py` 验证矩阵才能确认。

## 7. 没解决的问题（如实说明）

1. **缺少"玩家主动搭话"的通用样本。** v2 的上下文全部来自**真实剧情**，
   因此输入都是剧情台词。推理场景②③⑩（"三月七，你今天看起来很有精神啊。""今天走了一整天，好累啊。"）
   这类**日常闲聊式提问在语料中并不存在**。目前只能靠 `bare_line` 形态近似覆盖，
   但语义分布仍有 gap。彻底解决需要**合成**这类对话（会引入合成数据风险）。
   当前的 85 条角色语音样本部分缓解了这一点（问候/道别/烦恼…）。
2. **`val` 只有 68 条 / 9 个 mission。** 三月七数据总量只有 1357 条，5% 就只有 68 条，
   统计噪声较大（val_loss 的抖动可能大于真实差异）。若需要更稳的 val，
   建议提高到 8–10%（约 110–135 条 / 15–20 个 mission）。
3. **角色语音的上下文是合成的**（85 条，`synthetic_context=1`）。它们不是真实剧情，
   是按 `section` 合成的触发情境。虽然刻意对齐了推理场景，但仍属合成数据。
4. **没有验证"格式对齐"本身能否提升效果。** 父代理的实测显示训练格式 19.0 字 vs
   自然格式 11.5 字，但那是**旧模型**的对比；v2 数据训练后能否复现该收益，需实测。
5. **未做 tokenizer 级截断检查。** 训练脚本 `max_len=512`，v2 样本
   `user+assistant` 最大约 400 token（已用 `--max-total-tokens 400` 卡过上限），
   但不同 chat_template 的额外 token 未逐一验证。

## 8. 新数据的局限与缺陷

1. **单行样本存在长度偏置。** 地区配额内按长度降序优先选取（这是达成问题③目标的有意选择），
   会让单行样本比"随机抽样"略长。副作用：模型可能对"短促应答"场景（如只回一句「讨厌！」）
   学得不足。战斗语音层部分补偿了这一点。
2. **`scene_action` / `bare_action` 的动作旁白是从上下文里"回溯截取"的。**
   语料中"动作旁白紧贴三月七台词"的情况不多，脚本会在该台词之前的完整历史里回溯到
   最近一个合适旁白，并取以它结尾的窗口。这些窗口**都是真实连续的**语料片段（不是拼接），
   但"动作 → 三月七开口"的因果贴合度不如天然相邻的强。
3. **仍无法完全消除"分支导致的错位"。** 语料把同一处的并列选项按顺序平铺，
   脚本已折叠 choice 块并限制"一个样本最多 1 个 choice turn"，但剧情分支复述
   （如 POV 切换时同一句被记录两次）无法根除，只能靠 `重复台词过滤器` 兜底
   （为此丢弃了 40 条）。
4. **场景描述是规则推断的，不是游戏原生标签。** 如 `贝洛伯格，看看为什么有人堵路`
   这种描述是 `region` + `section` 拼接的产物，个别会略显生硬（但绝不含任务名）。
5. **3 条样本场景信息弱**（section 在游戏原文中被涂黑，只能退回地点）。
6. **`__voice__/*` 是伪 mission 名**，若下游代码假设 mission 名一定是真实任务名会受影响。

## 9. 结论

- 四个已确诊问题中，①②④ **已修复并有量化证据**；③ **已大幅改善**（13.9 → 28.9 token）
  但需要训练实测确认最终推理长度。
- 格式一致性检查**通过**：训练 user 段与真实推理 prompt 结构一致，元数据污染 0%。
- 20 条抽样人工评估：**格式自然率 100%，可用率 95%**。
- 主要遗留问题：**缺少日常闲聊式的"玩家主动搭话"样本**，以及 **val 集偏小**。
